---
name: code-review
description: 用户要求评审、检查、看看代码改动、PR 或某个文件时使用。
---

评审的目标是找出会出问题的地方，不是挑风格。按下面的顺序做：

1. **先搞清楚改了什么**：没有指定文件时，运行 `git status` 和 `git diff`（已暂存的用 `git diff --staged`）。看不懂意图的地方先问，不要猜。
2. **按严重程度逐项检查**，每一项只在真的有问题时才写：
   - **正确性**：逻辑是否符合意图；空值、空集合、零、负数、超大输入；并发与竞态；错误是否被吞掉或被错误地忽略。
   - **边界与兼容**：对外接口、配置、数据格式的改动是否会让旧数据或旧调用方出错。
   - **安全**：用户输入进入命令、SQL、路径、HTML 的地方；密钥或令牌是否被写进代码、日志或发给前端。
   - **测试**：新增的行为有没有测试；测试是不是真的会在行为出错时失败。
   - **可维护性**：只指出会让下一个人踩坑的问题（误导性的命名、重复的逻辑、没解释的魔法数字）。
3. **输出格式**：
   - 先用一两句话说结论（可以合并 / 建议修改后合并 / 有阻塞问题）。
   - 然后分三组列出：**必须改**、**建议改**、**可选**。每条写清楚：位置（文件和行）、问题是什么、会导致什么后果、建议怎么改。
   - 没发现问题就直说“没发现问题”，不要为了显得认真而凑意见。
4. 不要在评审时直接改代码，除非用户明确要求。
