1 结论

技术上可行，而且改动量比想象的小。原因是项目已经有两块现成的地基：

  • MCP 客户端（internal/mcp）已经能托管任意语言写的外部进程，把它的工具接进工具系统，并走统一的权限确认。它天然就是"工具插件"的协议。
  • internal/plugin 里已经定义了 Skill、斜杠命令、Hook、状态栏四类扩展的接口，状态栏脚本已经实现，只缺"从磁盘加载"和"接入内核"。

推荐做法：不发明新的插件运行时，把插件做成"一个目录 + 一份清单"，清单声明它带来的技能、命令、MCP 服务和钩子，由加载器分发给现有的各个注册表。

核心取舍

① 工具能力一律走 MCP：作者可以用任何语言，不用学新协议。② 界面不允许插件注入前端代码，只提供声明式表单和按钮。③ 插件是用户电脑上的外部程序，无法沙箱，安全靠"安装前展示清单 + 默认每次询问 + 密钥进钥匙串"。

分三期交付：先做不含可执行代码的声明式插件（技能、命令），再做工具插件和飞书，最后做钩子。预计总工作量 12–16 个开发日（粗估，见第 11 节）。

位置已有缺什么

3 总体架构

新增一个 PluginHost（放在 internal/plugin），负责扫描、校验、启停，并把每个插件带来的东西分发给已有的注册表。内核看不到"插件"这个概念，只看到更多的技能、工具和钩子。

4 插件包格式

一个插件是一个目录，根下有 plugin.json。安装位置固定，代码目录只读，运行时数据另放：

~/.myllmapp/plugins/feishu/        ← 插件代码（安装后只读）
  plugin.json                      ← 清单
  skills/feishu-docs/SKILL.md      ← 技能：给模型看的说明
  commands/summarize-doc.md        ← 斜杠命令：提示词模板
  server/feishu-mcp.js             ← MCP 服务（任意语言）
~/.myllmapp/plugin-data/feishu/    ← 插件自己的运行时数据（可写）
settings.json → plugins.feishu     ← 用户填的配置（密钥项存钥匙串，不落盘）

清单示例

{
  "id": "feishu",                       // 小写字母、数字、-，最长 24 个字符（会成为工具名的一部分）
  "name": "飞书",
  "version": "0.1.0",
  "description": "读取飞书文档和群消息",
  "min_app_version": "1.2.0",           // 低于此版本的应用拒绝加载
  "protocol": 1,                        // 对应事件协议版本，不匹配则拒绝加载

  "skills":   [{"path": "skills/feishu-docs"}],
  "commands": [{"name": "feishu-summary", "path": "commands/summarize-doc.md"}],
  "mcp": [{
    "name": "feishu",
    "command": "node", "args": ["${PLUGIN_DIR}/server/feishu-mcp.js"],
    "risk": "read",                     // 作者声明；用户在安装时确认后才生效
    "env": {"LARK_PROFILE": "${config.profile}"}
  }],
  "hooks":    [{"point": "pre_tool_use", "command": "node hooks/audit.js", "timeout_ms": 3000}],
  "subagents":[{"name": "doc-reader", "path": "agents/doc-reader.md"}],

  "config": [                           // 声明式设置表单，见第 7 节
    {"key": "profile", "label": "飞书应用配置名", "type": "string", "default": "default"},
    {"key": "app_secret", "label": "App Secret", "type": "secret"}
  ],
  "status":  {"command": "lark-cli auth status --format json", "ok_path": "ok"},
  "actions": [{"id": "login", "label": "登录飞书", "command": "lark-cli auth login --no-wait"}],

  "requires": {"commands": ["lark-cli"]},   // 缺少时在插件页提示怎么安装
  "network":  ["open.feishu.cn"]            // 声明会访问的域名（用于安装确认，不做强制拦截）
}

清单格式选 JSON 而不是 TOML：设置文件和前端都是 JSON，插件作者多数来自 JS/Python 生态。路径变量 ${PLUGIN_DIR}、${DATA_DIR}、${config.xxx} 由加载器展开，且路径必须落在插件目录内。

5 四类能力

按"风险由低到高"分层，每一层都能独立交付。

第 1 层 · 无可执行代码

技能 · 命令 · 提示词

  • 技能：SKILL.md（前置的 name、description + 正文），采用渐进加载：系统提示词里只放名称和一句话简介，模型需要时调用 read_skill（read 风险，免确认）读正文。
  • 斜杠命令：markdown 模板，支持 {{args}}；输入 /名称 参数 后展开成一段用户消息。
  • 子 agent 定义：提示词 + 可用工具白名单。

最容易写、最安全，应该最先做。

第 2 层 · 外部进程

工具插件（MCP）

  • 清单里声明一个 MCP 服务，由现有 mcp.Manager 启停和连接。
  • 任意语言实现；工具自动出现在工具表，走权限确认。
  • 风险默认 exec（每次询问）；作者可声明 read，经用户在安装时确认后才降级。
  • 停用 / 卸载插件时批量摘除它的工具。

飞书、Slack 都属于这一层。

第 3 层 · 介入流程

钩子（Hook）

  • 时机：user_prompt_submit、pre_tool_use、post_tool_use、turn_end。
  • 协议：外部命令，stdin 收一段 JSON（即现有 HookInput），stdout 回 HookDecision（放行 / 拦截 / 改写）。
  • 超时默认 5 秒；失败默认放行并提示，pre_tool_use 可声明失败即拦截。

能力最强，风险最高，所以放最后，并要求安装时单独确认。

状态栏脚本已经是现有能力（设置 → 状态栏），插件可以声明一个状态栏项，复用同一套实现，不属于单独的一期。

6 与内核的接合点

能力接入位置改动
技能core/prompt.go 追加技能清单；注册一个 read_skill 工具（read）小：约 80 行
斜杠命令前端输入框解析 /xxx，调用后端 ExpandCommand，展开后的文本再走 Send小：前端补全 + 一个绑定
MCP 工具把插件声明的服务合并进 mcp.Manager.Apply，配置带 source: "plugin:feishu"小：Manager 增加来源字段与按来源摘除
钩子runTool 在 Policy.Evaluate 之前调用 PreToolUse，工具执行后调用 PostToolUse；Send 开头调用 UserPromptSubmit；轮次结束调用 TurnEnd中：AgentConfig 增加 Hooks，需要补竞态和取消的测试
子 agentSubagents().Register无（调度器本身是另一项工作）
设置与密钥settings.json 的 plugins.<id>；密钥项走 internal/secret小

钩子放在权限裁决之前是有意的：它可以改写工具输入或直接拦截，但不能把"需要询问"改成"允许"。放行与否仍由权限策略决定，钩子只能让流程更严格。

7 界面扩展：只给声明式能力

Wails 的 WebView 能调用后端的全部绑定。如果允许插件往前端注入 JS，一个恶意插件就能直接调用 InstallUpdate、读设置、改权限。所以不开放前端代码注入，插件只能通过清单声明下面这些，由应用自己渲染：

声明界面表现
config插件页里的设置表单。字段类型：string、secret（存钥匙串，界面只显示"已设置"）、bool、select、path。值通过 ${config.xxx} 注入 MCP 的 env 和命令行。
status一个周期性执行的命令，输出 JSON；界面显示"已连接 / 未登录 / 缺少依赖"的状态点。
actions按钮。点击后运行声明的命令，把输出实时显示在面板里；输出里的 http(s) 链接可点击（例如登录授权页）。
requires检查本机是否有 lark-cli 等依赖，缺失时显示安装指引。
斜杠命令 / 状态栏项输入框补全列表、状态栏里的一项。

这套够覆盖"配置 → 登录 → 看状态 → 使用"的完整流程。如果以后确实需要自定义界面，再单独评估（例如放进带 sandbox 的 iframe 并只暴露受限的消息通道），不在本方案范围内。

8 安全模型

先说清楚边界：插件是在用户电脑上以用户权限运行的外部程序，无法真正沙箱。方案的目标是让用户在"知情"的前提下授予信任，并把误用的代价降到最低，而不是假装能防住恶意插件。

风险措施
安装了恶意插件安装前弹出确认，逐项展示：要启动的命令、提供的工具及风险等级、钩子、依赖的外部命令、声明访问的域名、需要的配置项。用户确认后才写入磁盘并启用。不做静默安装，不做自动更新。
插件工具悄悄做危险操作MCP 工具默认 exec，每次询问；作者声明 read 需用户在安装确认里勾选，且可以在权限规则里随时改回。现有的规则和工具开关对插件工具照常生效。
密钥泄露secret 类配置只存系统钥匙串；注入子进程时只放进该插件声明的环境变量；不发给前端，不写入插件目录和日志。
插件读取其他插件或应用的数据子进程的环境变量只继承白名单（PATH、HOME 等）和插件声明的项，不继承应用自己的密钥；数据目录按插件隔离（约定，非强制）。
钩子绕过权限钩子只能让流程更严格（拦截、改写输入），不能把 Ask 改成 Allow（见第 6 节）。
路径逃逸清单里的所有路径必须落在插件目录内（解析符号链接后检查，沿用 resolvePath 的做法）；安装包解压时拒绝 .. 和绝对路径（防 zip slip）。
来源被篡改 / 更新后行为变化从 Git 安装时记录提交哈希；更新是用户主动操作，并显示清单和脚本的变化；第一版不做插件签名，后续可复用自更新那套 ed25519 方案。
失控的进程统一的启动超时、调用超时、输出大小上限（沿用 100KB 截断）；应用退出时按进程组杀掉子进程（mcp 包已有）；Windows 上隐藏控制台窗口（sysproc）。
数据流向第三方模型插件读到的内容（如飞书文档、群消息）会作为工具结果发给当前选择的模型厂商。界面上在插件页和首次调用时明确提示；插件可声明 sensitive: true 要求每次调用都询问。

清单里的 network 只用于安装确认，不会强制拦截，应该如实告诉用户这一点，避免给人虚假的安全感。

9 生命周期与分发

stateDiagram-v2
  [*] --> 已下载: 选择目录 / 填 Git 地址
  已下载 --> 待确认: 校验清单
  待确认 --> 已启用: 用户确认安装
  待确认 --> [*]: 取消并清理
  已启用 --> 已停用: 停用
  已停用 --> 已启用: 启用
  已启用 --> 已启用: 更新（再次确认）
  已停用 --> [*]: 卸载
  • 安装来源（第一版）：本地目录、Git 仓库地址（可指定标签或提交）、zip 文件。内部私有仓库的访问凭据走用户本机的 git 配置，应用不保存。
  • 启用 / 停用：停用时摘除它的技能、命令、工具、钩子，并停止子进程；配置和钥匙串里的密钥保留。卸载时询问是否一并清除。
  • 兼容性：清单的 min_app_version 和 protocol 不满足时，插件显示"需要升级应用"，不加载；应用升级后不兼容的插件被自动停用而不是报错崩溃。
  • 冲突：插件 id 全局唯一；斜杠命令重名时加插件前缀（/feishu:summary）；工具名天然带 mcp__插件id__ 前缀。
  • 分发（后续）：先靠"填 Git 地址"。等有一批插件后，再做一个官方的索引仓库（一个 JSON 列表，含名称、地址、哈希），应用里可以浏览，仍然保留安装确认。
  • 与自更新的关系：应用更新不触碰插件目录；插件按自己的版本独立管理。

10 示例：飞书插件怎么落地

飞书官方有开源的 lark-cli（--as user 以本人身份调用，OAuth 登录，令牌在系统钥匙串，输出 JSON）。插件只需要把它包成几个只读工具，令牌始终留在 lark-cli 手里，应用不经手。

  participant A as 应用（插件页）
  participant P as 飞书 MCP 服务
  participant L as lark-cli
  participant F as 飞书
  U->>A: 点击「登录飞书」
  A->>L: auth login --no-wait
  L-->>A: 授权链接
  A-->>U: 显示可点击的链接
  U->>F: 浏览器里授权
  A->>L: 周期性 auth status
  L-->>A: 已登录
  U->>A: 提问「总结这篇文档」
  A->>P: feishu_read_doc(url)
  P->>L: docs … --as user --format json
  L->>F: 以用户身份读取
  F-->>L: 文档内容
  L-->>P: JSON
  P-->>A: 文本（截断到 100KB）
工具风险说明
feishu_read_doc(url)read读取云文档 / 知识库页面，转成 Markdown
feishu_search(query)read搜索文档或消息
feishu_read_chat(chat, since)read + sensitive读取指定群的最近消息；每次调用询问一次，因为内容会发给模型厂商
发消息、改文档exec第一版不提供

落地前要先验证（约半天）：lark-cli 读取文档和群消息的确切子命令与所需权限，官方文档里没有给出；租户是否需要管理员批准自建应用。需要在你的电脑上登录后实际跑一遍，再定工具的实现。

Slack 同理：做成另一个插件，共用"IM 插件"的约定（只读工具集 + 登录动作 + 状态检查），不需要内核改动。

11 分期计划

工作量按"开发 + 单元测试 + 三平台的联调"粗估，单位是开发日，实际会随你对界面细节的要求浮动。

第 1 期
3–4 天

声明式插件

  • 清单解析与校验、PluginHost、安装 / 启停 / 卸载（本地目录与 zip）
  • 技能（渐进加载 + read_skill）、斜杠命令、提示词片段
  • 设置 → 插件页（列表、启停、详情）；安装确认弹窗

验收：写一个纯 markdown 的插件，装上后模型能按需读取技能，输入 /命令 能展开；停用后立刻消失。

第 2 期
4–5 天

工具插件与声明式界面

  • MCP 服务由插件声明、按来源管理；风险声明与确认；环境变量白名单
  • config 表单（含 secret 进钥匙串）、status 状态点、actions 按钮与输出面板、requires 依赖检查
  • Git 地址安装（记录提交哈希）

验收：一个示例 MCP 插件能配置、登录、显示状态；停用时工具和子进程一并消失；密钥不出现在任何日志和前端。

第 3 期
2–3 天

飞书插件

  • 先完成半天的验证；再做 3 个只读工具、登录动作和状态检查；文档里写清数据流向

验收：在你的飞书租户里，用本人身份读取一篇文档和一个群的最近消息。

第 4 期
3 天

钩子

  • AgentConfig.Hooks、runTool 调用点、超时与失败策略
  • "只能更严格"的约束测试；钩子的单独安装确认
以后

按需再做

  • 子 agent 调度器；插件索引仓库；插件签名；Slack 插件；是否开放受限的自定义界面

12 测试策略

  • 清单与路径：非法 id、路径逃逸、符号链接、zip slip、版本不兼容，逐项有失败用例。
  • 生命周期：安装 → 启用 → 停用 → 卸载，每一步检查技能、命令、工具、子进程是否同步出现和消失（用现有的 mcp 测试桩）。
  • 权限：插件工具声明 read 但未经确认时仍按 exec 询问；规则和开关对插件工具生效；钩子无法把 Ask 变成 Allow。
  • 密钥：断言 secret 值不出现在前端绑定的返回值、事件和日志里。
  • 跨平台：Windows 上的路径、cmd 与 sh 差异、隐藏控制台；用现有的 Wine 流程覆盖。
  • 端到端：用 Playwright 在 wails dev 里装一个示例插件，走完"安装确认 → 配置 → 使用 → 停用"。

13 需要你决定的事

1. 谁会写插件？

只有你们团队内部，还是要对外开放？这决定第 8 节的安全投入：内部使用可以先不做签名和索引；对外开放则需要尽早做来源审核和签名。我的倾向：先按内部使用做，接口按对外开放来设计。

2. 界面扩展的边界

是否接受"只有声明式表单和按钮，不能注入前端代码"。我的倾向：接受，理由见第 7 节。

3. 钩子要不要做、什么时候做

钩子能力最强也最容易出问题。如果短期没有具体需求，可以推迟或砍掉第 4 期。我的倾向：先不做，等有真实场景（比如合规审计）再做。

4. 插件工具的默认风险

默认每次询问最安全，但读文档、搜索这类工具会被频繁打断。我的倾向：默认 exec；作者可声明 read，安装时用户确认后降级，并提供"本会话总是允许"。

5. 清单格式

JSON（推荐）还是 TOML（与 config.toml 一致）。

6. 私有插件仓库

公司内部的 Git 仓库需要凭据。我的倾向：使用本机已有的 git 配置，应用不保存任何凭据。

7. 先做飞书还是 Slack

你们用飞书，我建议先做飞书，并且在第 3 期开始前先花半天验证 lark-cli 的能力和租户权限。

本方案基于当前仓库代码（internal/plugin、internal/mcp、internal/core）整理，所列工作量为粗估。飞书 lark-cli 的能力来自其公开文档，具体命令和权限需要实际验证。
