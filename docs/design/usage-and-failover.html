用量统计与故障转移方案

把"用了多少 token、花了多少钱"按天展开，并给每个厂商配置独立的网络代理，再加上模型组的自动故障转移。参考了开源项目 magpie 的做法，但按本项目"自己就是 agent"的特点重新取舍。

1 结论

三件事都可行，建议按"用量 → 代理 → 故障转移"的顺序做。用量账本是后两者的基础：故障转移要靠它判断"谁用得最少"，也要靠它记录每次切换。

  • 用量统计：新增一张逐次调用的账本表（SQLite，和会话同一个数据库），在所有模型调用的唯一出口记录，按本地日期聚合。设置里新增"用量"页：今天 / 7 天 / 30 天 / 全部，每天一行，点开看按模型、按会话的明细。
  • 代理：每个厂商配置档可以单独设置 HTTP / HTTPS / SOCKS5 代理，另有全局默认。现在的请求只会读环境变量，从桌面启动的应用读不到，所以国内访问海外厂商时没法配置。
  • 故障转移：新增"模型组"：一个虚拟的厂商，由若干个"配置档 + 模型"按顺序组成。请求失败且还没有输出任何内容时自动切到下一个成员；失败的成员进入冷却，到期后再试探恢复。

和 magpie 的关键区别

magpie 是给 Claude Code、Codex 等其他工具用的本地网关，要在四种 API 协议之间互相转换。本项目自己就是 agent，故障转移可以直接放在进程内的 Provider 这一层，不需要网关，也不需要协议转换，工作量小得多。如果以后想把本工具的厂商配置开放给别的 agent 用，再单独评估网关。

预计总工作量 17–19 个开发日（粗估，见第 9 节）。其中故障转移最重，主要风险在于"换厂商后历史消息能不能被新厂商接受"（第 6 节）。

3 magpie 的做法：借鉴什么，不照搬什么

先说明依据的范围：我读了 magpie 的 README、docs/reference.md 的前 100KB 和 providers-accounts.md 的前 100KB。gateway-routing.md 只读到了前半部分，路由组五种模式的算法细节、故障转移的重试次数和冷却时长我没有读到，下面标"本方案自行设计"的部分都不是 magpie 的数值。

主题magpie 的做法（已核实）本方案的取舍
用量窗口today / 7d / 30d / all，可自定义最近 N 天或时长；可导出 CSV借鉴：同样的窗口，加"按天展开"
统计字段输入、输出、缓存读写、推理 token、调用次数；tries、handed_on（被转交的尝试单独成行，且不算作请求）；首字后的输出速度借鉴：失败 / 转交的尝试也记账，但不计入请求数
费用价格是 美元/百万 token，四个数：输入、输出、缓存读、缓存写；没有价格的调用不计入总花费，也不当作免费；总额在读取时按当前价格重算，所以改价格会改写历史借鉴：这三条规则都采用
价格来源自己设置的价格 → 厂商目录 → models.dev 的目录 → "同某模型"简化：自己设置 → 内置默认表 → 无价格；联网获取价格表放到后面
配额读取订阅 / 套餐 / key 的余额和配额窗口，保留 45 天历史，窗口重置前提醒已有：ChatGPT 的额度（状态栏）；其他厂商暂不做，各家接口不统一
路由组五种模式：smart（优先最快重置的订阅）、order（依次用，直到某个答不了）、rotate（每轮换下一个）、usage（优先用得最少的）、pace（优先每小时剩余周额最多的）；可嵌套借鉴 order / rotate / usage 三种；smart 和 pace 依赖各家的配额窗口，不做；不做嵌套
转移时机"上游在回复尚未发出任何内容前失败时，网关转向下一个候选"采用同一条规则：已经输出内容后不自动切换，避免内容重复或拼接错乱
会话粘性提示缓存有价值时，同一会话固定在回答过它的成员上借鉴：会话内优先沿用上一个成员，它失败才换
上下文超限请求停在某成员且已用到其上下文窗口的 95%，会换到能装得下更多的成员借鉴：收到"上下文超长"错误时换到窗口更大的成员
登录失效401 且原因是 token_revoked / invalid_grant 等，把账号标为已撤销，停止使用直到重新登录；token_expired 只刷新一次借鉴：认证类失败的成员长时间冷却，直到配置变化或用户手动恢复
代理每个厂商、每个账号都可以单独设置；查找顺序是 账号 → 订阅 → 全局；日志里的代理地址会去掉用户名密码借鉴：厂商级 + 全局，日志脱敏；账号级暂不需要
本地网关127.0.0.1:3425，四种协议互转，供其他 agent 使用不做：这是它的核心产品，我们不需要
插件中间件、隐私过滤模型、WebDAV / S3 同步onRequest / onEvent / onResponse 钩子；本地过滤模型；备份同步不做：与本需求无关（插件系统另见专门方案）

4 用量统计

4.1 记在哪里：所有模型调用的唯一出口

现在只有 callModel 里的对话调用会累加到会话，标题生成、上下文压缩、将来的子 agent 都绕过了它，所以账对不上。做法是在 Catalog.Get 返回 Provider 时包一层"计量包装"，所有走 Catalog 的调用都自动记账：

flowchart LR
  A["对话 callModel"] --> W
  B["标题生成"] --> W
  C["上下文压缩"] --> W
  D["子 agent（将来）"] --> W
  W["计量包装
记时间 / 首字 / 用量 / 结果"] --> G["模型组（可选）"]
  G --> P1["厂商 A"]
  G --> P2["厂商 B"]
  W --> L[("usage_events
SQLite")]

会话 ID、调用来源（对话 / 标题 / 压缩）通过 context 传入，包装层不需要知道会话的任何其他信息。

4.2 数据模型

在现有 sessions.db 里新增一张表（迁移 3），一次模型调用一行；故障转移时，每次尝试各一行：

CREATE TABLE usage_events (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  ts            INTEGER NOT NULL,              -- 开始时间，Unix 毫秒（UTC）
  day           TEXT    NOT NULL,              -- 本地日期 YYYY-MM-DD，写入时按用户时区算好
  session_id    TEXT    NOT NULL DEFAULT '',
  source        TEXT    NOT NULL DEFAULT 'chat',   -- chat / title / compact / subagent
  profile       TEXT    NOT NULL,              -- 实际应答的厂商配置档
  model         TEXT    NOT NULL,
  group_name    TEXT    NOT NULL DEFAULT '',   -- 经哪个模型组路由；直连为空
  try_no        INTEGER NOT NULL DEFAULT 1,    -- 第几次尝试
  status        TEXT    NOT NULL,              -- ok / error / cancelled / handed_on
  error_kind    TEXT    NOT NULL DEFAULT '',   -- rate_limit / server / auth / network / context / quota / other
  input_tokens  INTEGER NOT NULL DEFAULT 0,
  output_tokens INTEGER NOT NULL DEFAULT 0,
  cache_read_tokens  INTEGER NOT NULL DEFAULT 0,
  cache_write_tokens INTEGER NOT NULL DEFAULT 0,
  duration_ms   INTEGER NOT NULL DEFAULT 0,
  ttft_ms       INTEGER NOT NULL DEFAULT 0     -- 首字延迟，没有测到为 0
);
CREATE INDEX idx_usage_day ON usage_events(day, profile, model);
CREATE INDEX idx_usage_session ON usage_events(session_id);
  • 为什么单独存 day：按日分组如果每次用 SQL 的时区函数算，跨夏令时和 Windows 上容易出错；写入时算好，查询就只是 GROUP BY day，并且已记录的历史不会因为之后换时区而变。
  • 不存内容：只记数字和名称，不存提示词和回答，账本泄露也不会泄露对话。
  • 体量：一行约 100–150 字节，每天 500 次调用一年约 25MB，不需要分表；设置里提供"保留最近 N 天"，默认永久保留。
  • 失败的尝试：status = error / handed_on 的行不计入"请求数"，但计入 token（有的厂商失败时也会计费）；用于排查"为什么今天切换了这么多次"。

4.3 历史数据怎么办

已有会话只有累计值，没有逐次记录。两个选项：

  • 推荐：不回填。账本从升级那天开始记，界面上注明"此前的会话只有累计值"，并在"数据"页保留各会话的累计 token。
  • 备选：把每个旧会话的累计值记在它最后更新的那一天，标为"估算"。会让某一天虚高，不推荐。

ChatGPT 现有的 usage.jsonl 在首次启动时导入新表（profile = chatgpt），之后状态栏的额度也从新表读取，两套账合成一套。

4.4 费用

  • 价格表：ModelMeta 增加缓存读价和缓存写价，四个数都是 美元 / 百万 token。
  • 查找顺序：用户在界面里设的价格 → 配置档 models_meta → 应用内置的默认表（只放常见模型，随版本更新，并标注"可能已过期"）→ 无价格。
  • 无价格的调用不计入花费，也不当作免费，界面上写明"有 N 次调用没有价格"并给出补价格的入口（照搬 magpie 的规则）。
  • 读取时计价：账本只存 token，不存金额。改价格后历史花费同步改写，这是有意的：价格填错了可以更正。代价是无法回看"当时的价格"。
  • 订阅类厂商（ChatGPT 账号登录）：只显示 token，不计金额，因为按套餐额度而不是按量计费。
  • 币种：内部一律美元；界面可以切换为人民币，汇率由用户填写（不联网取汇率）。

5 网络代理

5.1 现状与问题

三个适配器都用 &http.Client{}，Go 默认只读 HTTP_PROXY / HTTPS_PROXY 环境变量。从开始菜单或 Finder 启动的桌面应用拿不到你在终端里设置的变量，所以国内访问海外厂商时没有办法配置；而国内厂商又不希望走代理。

5.2 设计

层级说明
厂商配置档的 proxy最高优先级。取值：留空（跟随下一层）、direct（强制直连，忽略环境变量和全局设置）、或一个代理地址。
全局默认代理设置 → 常规 里设置一次，所有没单独设置的厂商共用。
环境变量最后兜底，保持和现在一致。
  • 协议：http://、https://、socks5://（golang.org/x/net 已在依赖里，目前是间接依赖，只需提升为直接依赖）。
  • 认证：地址里可以带用户名密码；密码走系统钥匙串，不写进 settings.json（和 API Key 同一套存储）。
  • 实现：新增 provider.NewHTTPClient(cfg)，三个适配器都改用它，统一设置代理、连接超时和"等待首字节"的超时（现在没有）。
  • 测试连接：厂商页的"测试连接"按钮自动走所配置的代理，失败时区分"代理连不上"和"厂商拒绝"，给出不同提示。
  • 日志脱敏：错误信息和日志里的代理地址一律去掉用户名密码（照搬 magpie 的做法）。
  • ChatGPT 登录：登录流程和模型调用都走同一个代理设置，否则会出现"能登录但不能调用"。

Windows 的"系统代理"（IE / 系统设置里的代理）Go 默认不读。第一版不做自动读取，让用户显式填写；以后可以加一个"跟随系统"选项。

6 故障转移：模型组

6.1 概念

模型组是一个虚拟的厂商配置档，类型为 group，由有序的成员列表组成，每个成员是"配置档 + 模型"。在模型下拉框里它和普通模型并列，选中后所有请求经它路由。内核只看到一个 Provider，完全不知道背后有几个厂商。

{
  "name": "主力",
  "type": "group",
  "strategy": "order",                 // order | rotate | least_used
  "members": [
    {"profile": "anthropic",  "model": "claude-sonnet"},
    {"profile": "volcengine", "model": "deepseek-v4"},
    {"profile": "chatgpt",    "model": "gpt-6-luna"}
  ],
  "sticky": true,                      // 会话内优先沿用上一个成员
  "first_byte_timeout_s": 30
}

6.2 策略

策略行为适用
order（默认）永远从第一个健康的成员开始，它不行再用下一个"主力 + 备用"，最常见
rotate每个新会话（或每一轮）换下一个健康成员分摊多个账号 / key 的额度
least_used选今天 token 用得最少的健康成员（读用量账本）多个等价账号，希望用得均匀

三种策略之上都叠加会话粘性：同一会话已经用过某个成员时，优先继续用它（厂商侧的提示缓存按账号生效，来回换会让缓存全部失效，既慢又贵）；它不可用时才按策略重新选。

6.3 什么情况下切换

总规则：只有在一个成员"还没有输出任何内容"就失败时才自动切换。一旦已经向界面输出了文字、思考或工具调用，就不再自动换（换了会出现重复、断句错乱或工具调用重复执行），而是把错误显示出来，并给一个"用下一个模型重试"的按钮。

失败类型判定动作该成员的冷却（本方案自行设计）
网络 / 超时连接失败、TLS 错误、等待首字节超过设定值（默认 30 秒）切下一个30 秒起，连续失败翻倍，上限 10 分钟
限流429切下一个取 Retry-After；没有则 60 秒
服务端错误5xx、529 过载切下一个同"网络"
认证失败401 / 403（令牌刷新已由适配器内部处理过，仍失败才算）切下一个长冷却：直到配置变化或用户点"恢复"，不自动试探
额度用完ChatGPT 的 ErrUsageLimit，或厂商返回余额不足切下一个知道重置时间就到重置；否则 30 分钟
上下文超长400 且错误类型为 context length切到上下文窗口更大的成员；没有就走现有的上下文压缩不冷却（不是成员的问题）
请求本身有问题其他 400 / 422不切换，直接报错：换谁都一样会失败—
用户取消ctx 被取消不切换—

所有成员都不可用时，报错信息里列出每个成员的失败原因和剩余冷却时间，而不是只说"失败"。

6.4 成员的健康状态

stateDiagram-v2
  [*] --> 健康
  健康 --> 冷却中: 失败（记录原因和到期时间）
  冷却中 --> 试探中: 冷却到期
  试探中 --> 健康: 一次请求成功
  试探中 --> 冷却中: 再次失败（冷却翻倍）
  冷却中 --> 健康: 用户点「恢复」/ 配置变化
  健康 --> 已停用: 认证失败
  已停用 --> 健康: 重新登录 / 改配置 / 点「恢复」
  • 状态只放内存，应用重启后全部重置为健康：冷却是为了避免反复撞墙，重启后重新试一次的代价很小。
  • 试探用真实请求，而不是单独的探活：同一时间只放行一个请求去试探，其余请求继续用其他成员，所以用户不会因为试探而卡住。
  • 用户随时可以在界面上看到每个成员的状态点和剩余冷却，也可以手动恢复。

6.5 一次请求的流程

sequenceDiagram
  participant C as callModel
  participant G as 模型组
  participant A as 成员 A
  participant B as 成员 B
  participant L as 用量账本
  C->>G: Stream(请求)
  G->>G: 按粘性 / 策略选成员，跳过冷却中的
  G->>A: 发送请求
  A--xG: 429（尚未输出任何内容）
  G->>L: 记一行 handed_on（成员 A，限流）
  G->>G: A 进入冷却
  G->>B: 清洗历史后发送同一请求
  B-->>G: 流式输出
  G-->>C: 增量（附带"实际应答者 = B"）
  G->>L: 记一行 ok（成员 B，含 token）

6.6 最大的技术风险：换厂商后历史还能用吗

消息历史是中立格式，但各厂商对历史的要求不同。切换后同一份历史发给另一个厂商，可能直接被拒绝：

问题例子处理
思考块的签名Anthropic 的思考块带签名，只对原模型有效；其他厂商不认发给不同厂商前丢弃历史中的思考块（它们本来就只用于回显，不影响内容）
加密思考Anthropic 的 redacted thinking、OpenAI Responses 的加密推理项同上，丢弃
工具调用 ID 格式各家对 ID 的字符集和长度有要求适配器统一规范化，成对的调用和结果用同一个映射
图片目标模型不支持图片输入替换成一句文字说明，并在界面提示
上下文窗口备用成员窗口更小，放不下当前历史切换前估算；放不下就先压缩，或跳过这个成员
工具名 / 参数规则名字长度、字符限制不同（MCP 工具名尤其容易触发）沿用现有的名字规范，并在测试里覆盖

实现上，在 Provider 的接口上增加一个可选能力 PrepareHistory(msgs) []Message（每个适配器自己说明"我不能回放什么"），模型组在切换时对历史调用目标成员的这个方法。这部分必须先用真实的跨厂商会话做测试（Anthropic ⇄ OpenAI 兼容 ⇄ Responses 各方向），再决定哪些成员组合可以放进同一个组。

6.7 让用户看得见

  • 消息头：每一步现在显示"厂商 / 模型"，改为显示实际应答者；发生过切换时加一个小标记"由 A 转交"，悬停显示原因。需要新增一个事件字段（message_start 里的 provider / model 目前取自请求，转交后要更新为实际成员）。
  • 状态栏：选中模型组时显示"主力 → B"，B 为当前实际使用的成员。
  • 设置 → 模型厂商：新增"模型组"区块，可以新建、拖动排序、选策略；每个成员旁显示状态点、今日用量、剩余冷却，以及"恢复"按钮。
  • 用量页：按模型组筛选，并能看到每天"转交了多少次、各因为什么"。

8 安全与隐私

风险措施
故障转移会把对话发给另一个厂商这是本功能最实质的隐私影响。只有用户亲手加进模型组的成员才会被使用，不存在"悄悄换到没配置过的厂商"；转交发生时在消息上有明显标记；模型组编辑页写明"组内所有成员都会收到你的对话内容"。
代理账号密码泄露密码进系统钥匙串，不落盘、不进日志、不发给前端；日志和错误里的代理地址统一脱敏。
自建的恶意代理读取流量代理由用户自己填写，应用无法判断；界面提示"代理可以看到你的 API Key 和对话内容"（HTTPS 内容本身仍是加密的，但 CONNECT 前的目标域名可见，HTTP 代理地址若是明文协议则代理凭据可被嗅探）。
用量账本泄露内容只存数字和名称，不存任何提示词和回答；导出的 CSV 同理。
费用误导价格由用户 / 内置表提供，可能过期或填错；界面用"预估"，并标出无价格的调用数量，不显示精确到分的假象。
冷却被滥用导致全员不可用冷却有上限（10 分钟）；认证类的长冷却可以手动恢复；全员冷却时仍会放行一次试探，而不是直接拒绝所有请求。
失败重试造成重复计费已输出内容后不自动重试；失败的尝试单独记账，用户能看到。

10 测试策略

  • 账本：跨零点、跨时区、取消的调用、只有部分用量的失败调用；内存版和 SQLite 版共用同一组用例（沿用 store_test.go 的做法）。
  • 计价：缺价格、缓存价格缺失、超长上下文分档（如果以后加）、改价后重算。
  • 故障注入：给 fake 厂商加"第 N 次调用返回某错误 / 在首字节前超时 / 输出一半后断开"的脚本，逐行验证第 6.3 节的表格；冷却用可注入的时钟，不用真实等待。
  • 跨厂商历史：用真实录制的会话做夹具，断言清洗后的历史符合目标适配器的请求格式（现有适配器测试里已有请求体断言的做法）。
  • 并发：多个会话同时失败时只有一个试探请求；-race 必须通过。
  • 代理：用本地 HTTP 和 SOCKS5 代理验证走向；direct 与环境变量的优先级；日志里搜不到密码。
  • 端到端：Playwright 在 wails dev 里用 mock 服务制造 429，截图验证转交标记、用量页的按天展开和状态点。

11 风险

风险影响缓解
跨厂商历史不兼容转交后备用成员直接报 400，等于没有故障转移第 4 期最先做兼容性测试；对不兼容的组合在编辑页给出警告
各家错误格式不统一分类不准，该切的没切、不该切的切了分类逻辑集中在一处并用真实响应样本做夹具；无法识别的错误默认不切换
价格表过期花费估算偏离标注"预估"和价格表日期；价格可由用户随时覆盖
账本写入拖慢请求每次调用多一次写库写入放在异步队列里，失败只记日志，不影响对话
首字节超时设得不合适思考很久的模型被误判为失败而切换默认 30 秒只作用于"首个字节"（流式的第一个事件），而不是整个响应；每个模型组可调；推理类模型可单独放宽
我对 magpie 的了解不完整其路由细节我没读到，可能有我没考虑到的边界情况冷却、重试等数值都是本方案的独立设计，上线前用故障注入测试验证，而不是假定与 magpie 一致

12 需要你决定的事

1. 能不能接受"对话被转交给另一个厂商"？

这是故障转移的前提。模型组只包含你自己加入的成员，但如果某些厂商不允许你的数据出现在那里（合规），就只能在同一厂商的多个 key / 账号之间转移。我的倾向：允许，由你在模型组里自己决定谁在组里。

2. 币种和价格来源

只显示美元，还是可切换人民币？价格只用"内置表 + 手填"，还是以后联网更新？我的倾向：美元为内部单位，界面可切换人民币（手填汇率）；第一版不联网。

3. 历史数据要不要回填

见第 4.3 节。我的倾向：不回填，从升级当天开始记。

4. 输出到一半断开怎么办

现方案是不自动切换，给"用下一个模型重试"按钮。也可以让它自动重试（会丢弃已显示的半截内容并重新生成），但对工具调用已执行的情况不安全。我的倾向：保持手动。

5. 要不要做对外的本地网关

magpie 的核心产品，让 Claude Code 等别的工具共用你的厂商配置和用量统计。工作量很大（四种协议互转），与当前需求无关。我的倾向：不做，除非你有明确场景。

6. 事件协议是否升版本

只是给现有字段增加取值和可选字段，向后兼容，可以不升；如果希望旧前端明确拒绝新后端，则升到 2。我的倾向：不升。

7. 订阅类（ChatGPT 账号）的用量怎么展示

只显示 token 和调用次数，花费一栏写"套餐"。我的倾向：如此。

本方案基于当前仓库代码（internal/provider、internal/store、internal/core、internal/siwc）和 magpie 公开文档的已读部分整理；所列工作量为粗估，故障转移的数值参数为本方案自行设计，需要在实现阶段用故障注入测试校准。
