# 插件系统重设计（v3）：先让真实世界的插件能装、能用

状态：**设计提案**。阶段 A（§3.2 环境透传 + §3.3 启动可见）已实现；B、C、D 尚未实施。

和 [plugin-system-v2.md](plugin-system-v2.md) 的关系：v2 是 2026-11-01 在**没有运行任何真实流程**时根据代码静态审查写的，其中的“可用性诊断”（Ready / Needs Setup / 连接状态）已在 v1.7.9 落地。v3 是在**真正跑了一遍**之后写的：先复现，再设计，只针对复现到的问题。v2 里没被 v3 推翻的部分（安装向导、试用路径、跨平台验收）继续有效，不重复。

## 1. 复现：我实际跑了什么，看到了什么

方法：用本仓库构建的 `mosaicd`，临时 HOME 和工作区，通过它的 JSON-RPC 调用和界面完全相同的 App 绑定（`ListPluginCatalog` → `PreviewCatalogPlugin` → `InstallPlugin` → `ListPluginDiagnostics` → `ListCommands` → `ExpandCommand`），逐个走一遍。

| 场景 | 结果 |
| --- | --- |
| 市场里的纯技能/命令插件（hello-skill） | ✅ 安装即启用，诊断 `ready`，`/hello` 正常展开 |
| 市场里的 MCP 插件（echo-mcp，python3） | ✅ 诊断 `ready`，MCP 已连接，2 个工具注册 |
| 缺外部命令的插件（feishu，没装 lark-cli） | ✅ 诊断 `needs_setup`，写明缺 `lark-cli` |
| 刷新在线市场 | ✅ 能刷新，但线上列表就是仓库里同一份 8 个插件 |
| **一个 Claude Code 格式的插件**（`.claude-plugin/plugin.json` + `commands/*.md` + `skills/` + `agents/`） | ❌ **直接拒绝：“找不到 plugin.json”** |
| **一个 `npx` 启动的官方 MCP 服务器**（`@modelcontextprotocol/server-filesystem`） | ❌ 安装成功、显示“启动中”，**60 秒后失败**：`initialize: context deadline exceeded`，没有可读的原因 |

第二个失败我查到了原因，并单独验证：同一个服务器直接在终端里用 `npx` 运行 5.7 秒就起来了；但 Mosaic 启动**插件**带来的子进程时只给一份环境变量白名单（`internal/mcp/env.go`，为了不把厂商 API Key 泄露给第三方插件），白名单里没有 `NODE_EXTRA_CA_CERTS` 和 `npm_config_*`。用 `env -i` 加上和白名单完全相同的变量运行 `npm ping`，得到 `SELF_SIGNED_CERT_IN_CHAIN`；用完整环境则正常。也就是说：**凡是需要自定义证书、npm 镜像或代理配置才能联网的环境（公司网络、国内镜像），所有 `npx` / `uvx` 类插件都会卡 60 秒然后失败，而且界面上看不到 npm 的报错。** 这个沙箱走的是带自签证书的代理，所以复现得很干净；真实用户里最常见的对应情形是公司代理和 `npm_config_registry`。

没有覆盖到的（需要你告诉我，或需要真机）：Electron 界面里点击这些流程时的表现；Windows 上的 `npx.cmd`；你机器上具体是哪个插件、哪一步出的问题。

## 2. 问题归纳

1. **生态不通**：绝大多数现成的插件（Claude Code、Codex）都是 `.claude-plugin/` 或 `.codex-plugin/` 布局，Mosaic 只认根目录的 `plugin.json`；带 `agents/`、`hooks/` 的更是整包拒绝。用户拿到一个插件，十有八九装不上。
2. **自带的插件太少且太浅**：8 个里 6 个只是提示词模板。想“用上插件”的人没有可用的东西。
3. **MCP 启动环境过窄，失败不可读**：见上。同类的还有 `uvx`（`UV_*`、`PIP_*`）、`pip`/`cargo`/`go` 的镜像变量。而且启动阶段看不到 stderr，只能干等 60 秒。
4. **没有“试一下”**：装好之后用户不知道该做什么。（沿用 v2 的 D04。）

## 3. 设计

### 3.1 格式适配层：读懂别人的插件（解决 1）

新增 `internal/plugin/importer/`：纯函数，输入一个目录，输出 Mosaic 现有的 `Manifest`（以及一份“忽略了什么”的清单）。**只读文件，不执行任何东西。** 安装前预览阶段调用，失败不影响已有流程。

识别顺序：根目录 `plugin.json`（Mosaic 原生，行为不变）→ `.claude-plugin/plugin.json` → `.codex-plugin/plugin.json` → 没有清单但有 `skills/`、`commands/`、`.mcp.json` 之一（按目录推断，名字取目录名）。

| 来源组件 | 映射 | 说明 |
| --- | --- | --- |
| `skills/*/SKILL.md` | 技能 | 格式本来就一样 |
| `commands/*.md` | 斜杠命令 | 读 frontmatter 的 `description`、`argument-hint`；正文里的 `$ARGUMENTS`、`$1`…`$9` 替换为用户输入。**`allowed-tools` 只显示在确认页，不当作授权**——权限仍由 Mosaic 的权限系统决定 |
| `.mcp.json` / 清单里的 `mcpServers` | MCP 服务器 | stdio 和 http；`${CLAUDE_PLUGIN_ROOT}` 映射为 `${PLUGIN_DIR}`；风险档位照旧默认“执行”，需用户在确认页勾选信任 |
| `agents/`、`hooks/`、`lspServers` 等 | **不支持，忽略并告知** | 现在是整包拒绝（`agent_format.go`），这是最大的拦路虎。改为：可以安装，确认页和详情里明确列出“以下组件不会生效：hooks（2 个）、agents（1 个）”。hooks 是会执行代码的东西，**忽略是安全的方向**；绝不静默授予 |

不做的：不兼容它们各自的“插件市场”协议里的自动更新、不执行 hooks（见 §6）。

> 注意：上表和 marketplace 的字段细节来自我对这两种布局的了解，**没有在本次复现里拿真实插件逐项核对**（沙箱里只造了一个最小的 Claude Code 风格夹具）。阶段 B 开工的第一步是取几个真实的公开插件作为夹具，核对后再定映射表。

**marketplace 仓库**：很多插件以一个仓库里放多个插件的形式发布（根目录有 `.claude-plugin/marketplace.json`，列出 `plugins[]`，每项有 `source`，通常是仓库内相对路径）。“从 Git 地址安装”遇到这种仓库时，不再报错，而是列出里面的插件让用户挑一个（或多个）安装。

### 3.2 MCP 启动环境（解决 3）

插件子进程的环境 = 基础白名单（不变） + **工具链透传组** + 清单声明的变量。

工具链透传组按**名字规则**放行，目标是让包管理器能联网和找镜像，同时不把凭据交出去：

- 放行：`NODE_EXTRA_CA_CERTS`；以 `npm_config_` / `NPM_CONFIG_` / `UV_` / `PIP_` / `GOPROXY` / `GONOSUMDB` / `CARGO_` 开头的变量。
- **一律剔除**名字里含 `token`、`auth`、`password`、`secret`、`key`（不分大小写）的变量，例如 `npm_config__authToken`。
- **不放行** `NODE_OPTIONS`、`PYTHONPATH`、`LD_PRELOAD` 之类能改变程序加载代码的变量。

另外，确认页增加“允许该插件读取这些环境变量”的逐项勾选（插件清单里已有 `env` 声明机制，这里只是把用户的批准记下来），给规则放行不了的情况留一条出路。

### 3.3 启动过程看得见（解决 3）

- 子进程的 stderr 实时写入诊断，详情页显示“已等待 N 秒 + 最后几行输出”。卡在下载就能看到 npm 在下载或在报证书错误。
- 启动超时按启动方式区分：`npx` / `uvx` / `pipx` 这类第一次要下载依赖的，首次握手上限 120 秒（现在统一 60 秒），超时的错误信息写“首次运行需要下载依赖，请检查网络、镜像或代理”，并附 stderr 末尾。
- 失败后保留输出，提供“重试”和“复制脱敏诊断”。

### 3.4 装好之后能试一下（解决 4）

沿用 v2 的 P1：详情页列出插件的能力（技能、命令、工具），命令旁有“在输入框里使用”，MCP 工具旁有“只读试调用”（仅 `read` 档的无参工具）。不重复设计。

### 3.5 内置插件

不扩充数量，只做一件事：把 `echo-mcp` 之外再加一个**真正有用、不依赖外部登录**的内置插件作为样板（例如把官方 `filesystem` 或 `fetch` MCP 做成一键安装的目录条目，走 3.2 / 3.3 的路径）。让“MCP 插件能用”在新机器上有一个官方示范。具体选哪个等评审时定。

## 4. 兼容与安全

- 原生 `plugin.json`（protocol 1）一个字段都不改，已装的插件行为不变。
- 适配层只读文件；导入产生的 `Manifest` 仍然走现有的校验、确认页、权限档位。
- 忽略组件不降低安全：hooks / agents 不执行就是不存在。
- 透传组的规则偏保守，且不放行任何可能含凭据的名字；新增放行项需要改规则并加测试。
- 对应的测试：每条映射一个夹具插件（真实结构的最小副本）；环境透传规则的表驱动测试（含 `npm_config__authToken` 必须被剔除）；用假 MCP 服务器验证“慢启动期间能看到 stderr”和“120 秒/60 秒的分档”。

## 6. 暂不做 / 需要你决定

- **hooks**：Claude Code 插件里最常见的“高级”组件，会在工具调用前后执行任意命令。支持它等于给插件一个绕过权限弹窗的入口，需要单独设计（只允许在确认页逐条批准的、沙箱化的子集）。本版本只忽略。
- **agents（子 agent）**：Mosaic 内核没有对应概念，需要先有子 agent 的设计。本版本只忽略。
- 远程 MCP 的 OAuth（v2 的 P2）。
